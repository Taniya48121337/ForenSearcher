# SFT 训练数据合成方案（一页纸，2026-09-21，待签字）

这份文档把"训练数据从哪来、哪些能进、每行带什么标签、放在哪"一次定下来。定了以后 export 模块照着写，后面每一轮 RSI 都按同一套规矩出数据，不再临时拍板。训练本身不急，但规矩要先立。

## 一、一行训练数据是什么

一行 = 某个角色在某个状态下的**一次决策**：`system`（规格里的 student_prompt）+ `user`（该时刻的状态，用状态渲染器按训练档位现场渲染）+ `assistant`（一个 JSON 动作或最终报告/答案）+ `images`（该次决策实际附给模型的图片路径）。loss 只算 assistant。HI 和 GIA 各自一个文件，不混。

状态**不存旧渲染结果**，存的是原始 payload 的定位（run、workspace、turn），导出时用当时的规格版本和指定档位重新渲染。这样改了渲染器或规格，重新导出即可，旧数据不会带着过时格式进训练。

## 二、行的三种来源

| 来源 | 怎么来 | 用途 | 现状 |
|---|---|---|---|
| A. 真实轨迹 | 教师（gpt-6-astra 等）实跑 run 目录里的每一步 | 主体正例；也是 B、C 的起点 | 已有 51 个 run，corpus 里 hi 303 / gia 37 行是它的前身 |
| B. 同状态再生 | 从真实轨迹的某一步取 store 快照 + 渲染后的状态，让教师重出一步 | 给反例配"同状态正例"；对稀少动作类型扩样 | 依赖 perturb.snapshot（已有）+ 单步调用（要写） |
| C. 扰动对照 | 用 perturb 的 mask / replace / inject 改证据，教师在改后的状态再决策，按 Expectation 判它有没有跟着变 | 教"证据变了结论要变"；也是核验器校准的靶子 | perturb 已有，evaluate 已有 |

第一期只做 A；B、C 在核验器校准完成后接入。

## 三、哪些行能进（入选规则）

规则按顺序过，任何一条不过就不入正例：

1. 规格一致：该行的 system 与 `specs/<role>@<ver>` 的 student_prompt 哈希一致；不同规格版本的行不混在一个导出里。
2. 硬检查：第一层 exec_checks 无 hard 错误（引用的 E 存在且可见、数字/日期在来源里、案卷断言不违反）。
3. 处置：所在工作区的报告 verdict 为 **positive**；GIA 行要求该 run 的最终答案通过案卷的 answer 检查。verdict 为 negative 或 uncertain 的工作区，其**全部**步骤不入正例（不做"污染 Finding 之前的步骤仍算好"的细分，宁可少要）。
4. 动作有效：assistant 必须是合法 JSON、动作在规格允许的集合内、引用的 E 都在当时状态里可见（`_visible_ids` 的并集口径）。
5. 去重：同一 case_family 的行按上限抽样（暂定每个 case_family ≤ 40 行 HI、≤ 8 行 GIA），避免 videosham 一个 case 占一半。

反例（rejected）：在核验器过校准之前，negative 报告**只用来排除**，不作为训练反例；校准通过后，带 error 标签的步骤才进 `*_rejected.jsonl`，供 DPO / 对照学习用。

## 四、每行必带的可追溯字段（metadata）

`role`、`origin`（A/B/C）、`run`、`workspace`、`turn`、`case_id`、`dataset`、`teacher_model`、`spec`（`hi@0.1.0`）与 `spec_hash`、`state_renderer`（`compact_8k` 等）、`verifier`（`verifier@0.1.0`）、`judge_model`、`verdict`（positive/negative/uncertain）、`error_types`（该工作区的错误类型列表，正例为空）、`tainted`（该步产出的 Finding 是否被污染）、`perturbation_id`（C 来源才有）、`exported_at`。

有了这些，任何一行都能回溯到它是哪个 run 的第几步、当时用的什么规格和渲染、谁核验的、核验结果是什么；RSI 第 n 轮改了规格或核验器，第 n+1 轮重新导出时自然分开。

## 五、放在哪、怎么命名

```
experiments/sft_data/export/<日期>_<spec>/
    hi_accepted.jsonl   hi_rejected.jsonl
    gia_accepted.jsonl  gia_rejected.jsonl
    manifest.json      # 行数、来源分布、动作类型分布、case_family 分布、所用 verdicts 文件、规格 hash、渲染档位
```

正反例分文件，不靠一行里的字段区分；manifest 是这批数据的"出厂单"，训练脚本只认 manifest 里列出的文件。

## 六、与推理保持一致的两条硬约束

- 训练用的渲染档位必须与目标部署一致：本地 4B 用 `compact_8k`，服务器模型用 `compact_16k`；同一批数据只用一个档位。
- 训练时看到的图片数量与限制（`image_input_limit`、8 张 GIA 预算）要与部署配置一致，行里的 `images` 就是当时真的附了的那几张，不多附。
