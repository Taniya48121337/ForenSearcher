# datagen 第四块砖：版本化规格 specs（2026-09-15）

位置：`src/foren_searcher/datagen/specs.py`、`bootstrap.py`；生成物在仓库根目录 `specs/`；测试 `tests/test_datagen_specs.py`（14 项）。

## 解决什么问题

以前"改提示词"就是把 `actor_generation_r7.txt` 改成 `r8`，给老师傅（教师模型）的办案注意事项直接拼进了学生的 system prompt，事后没人说得清某一批数据是按哪一版规则生成的。自我发展循环要求每一轮都能回答"这轮改了什么、改动针对哪种错、数据是按哪版产的"，所以规格必须像代码一样有版本、有指纹、有变更记录。

## 一个版本 = 一个目录

```
specs/hi@0.1.0/
    spec.json               角色、版本、父版本、harness 参数、changelog、hash
    student_prompt.md       给实习生看的岗位说明书：进训练 system 的固定文本
    teacher_instruction.md  给老师傅看的办案注意事项：只给教师，不进训练输入
    rubric.json             评分条目，每条绑定一种 ErrorType，标 presence / absence
```

`hash` 是对 student_prompt、teacher_instruction、harness 参数、rubric 四样内容算的 SHA-256。以后每一行训练数据的 metadata 都写这个 hash，任何一行都能追溯到规格版本；已发布目录里的文件被改动，`Spec.load()` 会因为 hash 对不上直接报错——想改就必须发新版本。

## 升号规则（`validate_bump`）

student_prompt 变了就是训练输入分布变了，必须升 minor 或 major（0.1.0 → 0.2.0）；只改教师指令、harness 参数或 rubric，升 patch（0.1.0 → 0.1.1）。这样看版本号就知道"训练分布变过没有"。新版本的 changelog 必须写明 `targets`——针对 22 种错误里的哪几种——否则不通过；这是把"改规格"和"错误分布"强制挂钩的地方，也是后面算"改动方向与错误分布一致率"指标的数据来源。什么都没改就发版，同样拒绝。

## rubric 条目

每条条目有：id、绑定的错误类型、axis（`absence` = "不得……"，`presence` = "应该……"）、文字、角色、可选的严重度覆盖、适用条件、可引用的 E 编号（案例专属条目用）、`replayable`（同一条目对同一段旧记录在新旧版本下判定应一致，用来测 rubric 漂移）。条目角色必须和错误类型允许的角色一致，例如 `premature_finish` 不能出现在 HI 的 rubric 里，代码会拦。

## 初始版本 hi@0.1.0 / gia@0.1.0（`bootstrap.py`）

student_prompt 直接取运行时正在用的常量（`local_models._HI_MULTIMODAL_SYSTEM_PROMPT`，GIA 的主提示 + 首轮派工变体以注释分隔）；teacher_instruction 取试点的 `actor_generation_r8 + actor_evidence_retention + actor_report_r6` 和 `actor_gia_r2`；rubric 按错误清单逐类生成"不得"条目（HI 17 条、GIA 11 条），再加少数"应该"条目。测试里有一条"漂移检查"：规格里的 student_prompt 必须和运行时常量一字不差，直到运行时改为从 `specs/` 读取为止。
