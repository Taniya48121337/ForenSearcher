# datagen 第五块砖：三层核验器 verify/（2026-09-15）

位置：`src/foren_searcher/datagen/verify/`（context、exec_checks、anchored、sufficiency、verdict、judges、reverify）。测试 `tests/test_datagen_verify.py`（15 项，含对试点 run `averimatec_441_q0_r1` 真实证据库的冒烟）。

## 和以前的评审有什么不同

以前：评审员拿着演员当时看到的桌面（分页截过的正文片段 + 附图）按七个维度打 0–4 分，评审员和教师是同一个 Codex 账号，最后只留 3–4 分的行。它核的是"演员看到的片段能不能撑住结论"，不是"证据原文能不能撑住结论"，也说不出错在哪一类。

现在：三层、逐条 Finding 核对、每条错误从 `errors.py` 的 22 种里挑名字、核验模型必须与教师分离。

## 三层各做什么（大白话）

第一层 `exec_checks`，纯程序，不花钱。查：引用的 E 在证据库里存不存在、提交报告那一刻看不看得见（从 trajectory 的最后一次 model_input 取可见集合）、COMPLETED 报告是不是空的、Finding 有没有引用、结论里的数字（≥10 或带小数）能不能在所引 E 的原文里找到；有案卷（`cases.py`）时再查：来源是否踩了排除名单、状态和案卷标注是否一致、应有的实体/标签/数值/日期/时间区间有没有出现、必需证据有没有被引用。判得死的记 `hard`（引用不存在、踩排除名单、必需证据没引用却报 COMPLETED），拿不准的记 `flag`（数字不在文本里——可能来自图片或计算），交给第二层。

第二层 `anchored`，模型逐句对原文，分两步。第一步对每条 Finding 的每条所引 E：核验模型只看"这句话"和"这条 E 的全文或图片"（从 Store 取全文，最长 2 万字符），不看任务、不看演员桌面，列出这条 E **支持了句子的哪些部分**、**反驳了哪些部分**，每一部分都带原文引语；文本来源的引语由程序回查是否真的在原文里（去空白、统一引号后子串匹配，≥6 字符），对不上的整条不采信；句子里讲别的材料/别的时刻的部分，这条 E 管不着，既不算支持也不算反驳。第二步对每条 Finding 汇总：把各 E 已核实的支持片段交给模型，问"句子里还有哪些实质部分没有任何来源支持"（限定语、保守措辞、由已支持数字直接算出的结果不算）。映射：有部分被反驳 → `wrong_citation`（critical，span 是那一部分；模型提示细字读错/口径不一致时改记 `misread_fine_text` / `sloppy_numeric`）；有实质部分无支持 → `unsupported_assertion`（span 是那一部分，不是整句）；来源只是转述而句子写成事实 → `attribution_drift`；模型提示以偏概全 → `scope_overreach`。图片 E 需要像素，核验模型看不了图时记为 pending；模型输出坏 JSON 重试一次，仍坏记 pending，不让整个 run 报废。

为什么是"部分"而不是"整句三态"：第一版对每对 (Finding, E) 只给一个三态，规则"只支持一部分算 not_found"。在 65 份真实报告上跑出来 474 对判定里 401 对 not_found、60 份判负——逐条看是核验器错了：报告里的句子几乎都是复合句（"41 秒可见餐盒；48 秒女子举盒；51.48 秒食物不可见"），每条 E（一帧、一页）天然只支持其中一部分，合起来才是全覆盖。另一个真实误判：拿 B 视频的一帧去反驳句子里关于 A 视频的描述。第二版针对这两点改。

第三层 `sufficiency`，模型看整份报告。输入任务全文 + 案卷必需证据清单 + 报告，回答每项要求 covered 没有、仅凭报告能否回答、状态应为什么。映射：案卷清单里的要求未覆盖 → `omitted_required_fact`（模型自己从任务文字归纳的要求只留在 raw 里作参考——第一次三层跑下来它把"准确说明来源与适用范围"这类套话也算成缺项，65 份报告报了 107 条，噪音太大）；报 COMPLETED 但有 must_cite 项未覆盖 → `completed_without_finishing`；报 INCOMPLETE 但已能回答 → `incomplete_though_answerable`。与第一层重复的按类型/键去重。

## 处置与污染

`Verdict`：错误列表、`disposition`（任一 critical 定错或 ≥2 个 major → negative；有 pending 或只剩 flag → uncertain；否则 positive）、`tainted_findings`（含传播型错误的 Finding，按 `errors.py` 的 propagates 规则）、跑了哪几层、每条判定的引语、核验器版本、核验模型名、规格 hash、渲染档位。一行一个写 `verdicts.jsonl`，可读回。

## 重核试点（第 0 轮错误分布）

`python -m foren_searcher.datagen.verify.reverify --runs experiments/sft_data/runs --out experiments/sft_data/verdicts_r0.jsonl` 遍历每个 run 的 `store.sqlite3`，对每份已发布的 Workspace Report 跑核验，输出 verdicts 和一份 summary（处置分布、各错误类型计数、含定错的报告数、被污染的 Finding 数、pending 原因）。默认 `--judge none` 只跑第一层；`--judge openrouter --model <与教师不同的模型>` 跑三层，密钥仍从 `.local/openrouter.json` 读，记账角色 VERIFIER。`scripts\重核第0轮.cmd` 是第一层版本的一键运行。

### 第 0 轮第一层的首次结果（2026-09-16，本机 51 个 run、88 份报告）

第一版跑出 35 个 `fabricated_evidence_id`（9 份报告 negative），逐条看全是误报：可见性检查只取了最后一次 model_input 的 `evidence_view`，而卡片区只保留 12 张，早先读过、后来被挤出卡片区但仍在 focus / 附图里的 E 被判成"不可见"。已改为取该工作区全部 model_input 里出现过的 E 的并集。另外数字比对有两个 bug：整数用 `format(x, "g")` 只留 6 位有效数字（3,735,245 变成 3,735,240），PDF 表格里 "3 735 245" 这类分组写法找不到。已改为整数保留全部位数、允许 1‰ 相对误差、以及去分隔符后的数字串匹配。

修正后在云端 5 个 run（21 份报告）重跑：硬错 0，flag 42（其中 34 条引用了图片帧、数字可能来自像素；其余 8 条是换算/求和得到的数字，如 "R493.1 million ≈ 493,100,000"、几行相加的合计），全部留给第二层判。也就是说：**第一层能判死的错在试点报告里基本没有；真正的问题（无据断言、以偏概全、转述当事实）只有第二层对原文才能查出来**，这与审计文档里"评审员没重读原文"的判断一致。

重核时 GlobalStore 打开会执行建表脚本并切 WAL，会动原 store 文件的修改时间；现已改为先复制到临时目录再打开，原始 run 目录不再被碰。

## 已知缺口

- 图片证据的第二层需要能看图的核验模型；OpenRouterJudge 已按 visual_qa 的格式附图，但未在真实模型上试过。
- 重核时还没有案卷（cases/）可用，所以来源排除、必需证据等案卷断言在第 0 轮不生效；案卷化落地后加 `--cases`。
- 核验器本身的准确率要用扰动器（perturb.py）注入的已知错误来校准（calibrate），尚未写。
