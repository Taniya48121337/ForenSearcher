# 数据生成框架审计（2026-09-15）

对象：`experiments/sft_data/` 的 15 个脚本、rubric_r6、演员指令 r7/r8、报告指令 r6，以及开发集语料 `corpus/gia_development.jsonl`（37 行）、`corpus/hi_development.jsonl`（303 行）。目的：回答"现在这套数据构造能不能直接拿去训练、能不能承载 DESIGN.md 第 8 节的自我发展循环"。结论先说：**两个都不能。** 不是某个脚本写坏了，而是这套流程的目标是"筛出好样本"，而循环需要的是"记录并分类所有错误"，方向相反。

---

## 一、现在的流程是什么

一个案例变成一行 SFT 样本要经过八步：`collect_validation.py` 选案例 → `run_case.py` 跑调查（教师 Codex CLI 每一步开一个全新会话，通过 `cli_generator.py`）→ `audit_run.py` 核对"这步输出真的被执行了" → `judge_run.py` / `judge_by_actor.py` 让另一个 Codex 会话按 `rubric_rN.md` 给每个目标打 0–4 分 → `export_sft.py` 只导出 3–4 分且无关键未知的步骤 → `assemble_corpus.py` 汇总成四个 jsonl 并检查开发/保留不重叠 → `check_student_inputs.py` 用 Qwen3.5-9B 的模板核对 label mask。另有两条旁路：`gia_text_states.py` / `gia_visual_states.py` 拿已有证据换问题构造离线 GIA 状态；`repair_terminal_report.py` 从报告提交前的状态用新指令重生成报告。

评审到底核什么：评审员拿到的是演员当时看到的 `model_view` 渲染（含 6000 字符分页后的正文片段）加全部附图，按七个维度打分（execution 10、visibility 15、grounding 25、task 15、decision 15、uncertainty 15、efficiency 5），再对每个目标给 `disposition / target_rating / critical_unknown`。**它不会重新打开网页、不会重新解码视频、看不到分页截掉的正文**，所以它核的是"演员看到的片段是否支持结论"，不是"证据原文是否支持结论"。评审员和教师是同一个账号下的 Codex CLI。

## 二、数据质量的具体问题

**监督信号极薄。** HI 的 assistant 输出中位数 170 个字符（约 57 token），88% 的行是 `{"action":..., "arguments":..., "focus_evidence_ids":[]}` 这种纯动作 JSON，没有推理、没有理由。输入端中位 14K token、最大 34K。全部 303 行的监督 token 约 2.9 万，输入 token 约 424 万，比例 1:145。教师的推理没有被采集（Codex CLI 的 `--json` 事件只有 `agent_message`）。带"为什么"的只有 35 行报告（11.6%）。

**动作是程序性的，不是决策。** 26 行 assistant 完全相同：`INSPECT get_frames count=8 on E1` 出现 7 次、`READ_RECORD E4` 4 次。这些是"第一步先抽 8 帧"式的默认动作，学生学到的是套路。

**训练输入长度和训练预算不匹配。** 仅 system prompt 就 2.5–3.9K token；整行估算 ≤4K 的 HI 行 0 条、≤8K 47 条、≤16K 219 条。项目自测全量 826 行里 369 行超 16K、45 行超 32K。最重的是 `history`（HI 平均 10.6K 字符）和 GIA 的 `latest_reports`（11.2K 字符）。这是运行时状态渲染决定的，导出脚本裁不了——**不改渲染器，循环每轮产出的数据都训不了**。

**system prompt 不是一个模板。** HI 有 10 种，GIA 有 9 种，因为 `cli_generator.py` 第 59 行把给教师的生成指令（`actor_generation_r7/r8.txt`，内容是"数据生成要求""不因'再确认一下'反复切换"）直接拼进 system prompt，随行进入训练输入。学生同时看到 10 种"规格"，训完无法归因哪个行为来自哪段规格；循环里"修订规格"这个动作会直接污染训练分布。

**评审版本混杂、只有正例。** HI 开发集 225 行（74%）是 rubric r2 评的，r4/r5 各 21/15 行，**没有一行是 r6 评的**；入库后只剩 3/4 两档（69%/31%），0–2 分的目标散落在各 run 的 `excluded_targets.json`，没有汇总，不进语料。循环最需要的错误分布数据在导出阶段被扔掉了。

**单案例集中。** HI 前三个案例家族占 40.9%，其中 `averimatec:63` 一个问题跑了 5 种来源条件共 46 行；GIA 前三占 59.5%。68% 的 HI 行来自第一轮第一个工作区。

**评审漏判有实证。** `candidate_exclusions.json` 三条都是评审给 3 分、人工复核发现事实限定错误（"批准拨付"写成"直接拨付"）。两条 `findings: []` 的空 INCOMPLETE 报告被打 4 分入库——教给学生的是"搜不到就交空报告"。r5→r6 重评同一轨迹分数不变，文档自认"没有证据表明 r6 提高了准确率"。

**其他。** `dataset` 字段大小写混用（`true` / `VideoSham` / `AVeriTeC`）；上传的语料没有 `images/` 目录时无法直接训练；教师绑定 Codex CLI 且路径硬编码，与服务器上 vLLM 起 Qwen3.5-122B 的计划不兼容。

## 三、与自我发展循环的差距

现有脚本能对上循环的只有"跑调查"这一步（`run_case.py` + `cli_generator.py`），其余各环节的状态如下。

核验器：现在是整体打分器，一个会话评整条轨迹给 0–4 分和自由文本理由，不逐条 Finding 对照所引 E 的原文，评审模型与教师相同——正是 S³Gym 报告 ρ≈-0.01 的自评设置。

错误类型分类：完全缺失。`critical_errors` 和 `reason` 全是散文；`rubric_r6.md` 第 41–52 条和"事实状态限定"一节其实已经把类型写全了，只是没有变成枚举。

诊断：靠人读 `judgment.json` 写进 `构造方法实测分析.md`；没有跨迭代曲线。

修订：手改文件名后缀（rubric r2→r6、指令 r3→r8），改动不与错误类型绑定，rubric 和演员指令同时改导致无法归因，没有 diff 记录。

对照轨迹：`repair_terminal_report.py` 和 `gia_*_states.py` 只导出新的正例，旧的负例被丢，不成对；`calibrate_rubric.py` 的 12 条手写正负例是给评审员做单元测试的，不是给学生的。

训练与留出门控：训练 0 次；`construction_validation` 门控的是"数据构造方法"（用评审分），不是训练后的学生；保留集已泄漏（392、1707、660 被用来改口径）。

版本化规格：没有 schema、没有 hash，行级只有一个 `assessment` 字段。

与循环直接冲突的三条设计：只导出 ≥3 分的正例；教师指令拼进 system prompt；同一案例跑多种变体当扩增（循环里这是混淆变量）。

## 四、重构建议

### 4.1 新的模块划分

```
datagen/
  errors.py     错误类型枚举（唯一定义处）
  specs/        版本化规格：hi@x.y.z.yaml、gia@x.y.z.yaml
  cases/        案例池：数据集标注 → case.json（含 split、family_key、source_policy）
  run/          教师执行：case.json + spec@version → episode/
  verify/       离线核验器：episode/ → verdicts.jsonl（逐 Finding、逐动作、带错误类型）
  diagnose/     错误分布与目标形成：verdicts[] → diagnosis.json（含跨迭代 trend）
  revise/       规格修订 + 对照轨迹：diagnosis + spec@v → spec@v+1、contrast.jsonl、revision_log.jsonl
  export/       打包：episode + verdicts + spec → sft/{hi,gia}.jsonl 与 rejected.jsonl（负例必须保留）
  gate/         留出门控：两个 checkpoint + heldout → gate.json（方向一致率、核验分↔提升相关性）
```

### 4.2 关键契约

`verdicts.jsonl` 每行一个 step：`findings[].checks[]` 逐条写 `{evidence_id, support: supports|contradicts|absent|unreadable, quote, method: reread_store|pixels}`——`method` 是硬性要求，核验器必须重读 store 里的原文或像素，不能只看演员 history 的渲染；`errors[]` 用枚举；`score` 是 0–1 连续分，只用于相关性分析不做筛选阈值；`disposition: positive|negative|context|unknown`。

`specs/hi@0.3.2.yaml`：`student_prompt`（进训练 system，改动升 minor）与 `teacher_instruction`（只给教师，不进训练输入，改动升 patch）分开；`harness_params`（image_input_limit、read_page_chars、max_model_view_chars、state_renderer）；`changelog[].targets` 绑定错误类型；`hash` 写进每行 metadata。运行时隐式拼接的 3846/5059 字符角色提示也纳入 `student_prompt`。

`export` 的行 metadata 新增：`spec_version`、`verifier_version`、`verifier_score`、`errors`、`sample_kind: positive|contrast_good|recovery`、`contrast_of`、`input_tokens_est`、`supervised_tokens_est`。

### 4.3 错误类型枚举（初稿）

Finding 级：unsupported_assertion、wrong_citation、fabricated_evidence_id、source_restriction_miss、attribution_drift（"来源声称 X"写成"X 成立"；批准/执行阶段互换）、scope_overreach（少数帧推全片）、misread_fine_text、sloppy_numeric、omitted_required_fact。状态级：completed_without_finishing、incomplete_though_answerable、empty_report。动作级：illegal_action、redundant_action、evidence_dropped、wrong_tool、ignored_feedback。GIA 级：task_not_gap_driven、premature_finish、unnecessary_round、dependent_sibling_tasks。环境级（不算演员错但要记）：env_contamination、env_tool_failure。每个错误带 severity、span、evidence_ids、verifier_method。

### 4.4 对照轨迹三种生成方式

同状态重生成（泛化 `repair_terminal_report.py` 的思路到任意 step，用 spec@v+1 让教师重出，核验器确认新输出不含种子错误类型，输出 `{state_ref, bad, good, spec_from, spec_to, error_type}`）；错误注入（对正例程序性改写：改 E 编号、INCOMPLETE 改 COMPLETED、去限定词、换数值口径，用于校准核验器，替代手写的 12 条）；恢复轨迹（负例前缀 + 从该 step 继续执行的正确后缀）。

### 4.5 现有脚本处置

改一改复用：`run_case.py` 的 `prepare_case()` → cases/；`cli_generator.py` 的每步落盘模式 → 换成 `TeacherClient` 抽象（vLLM/OpenAI 兼容，保留 thinking）；`audit_run.py::link_events` 原样进 run/；`judge_run.py` 的结构校验思路 → verify/，但改成逐 Finding 核验且核验模型≠教师，七维加权分废弃；`repair_terminal_report.py::RecordedInputGenerator` → revise/ 的同状态重生成；`gia_*_states.py` 保留但 CASES 字典改数据文件；`export_sft.py` 保留 `<image>` 对齐和 loss_scope，去掉硬阈值、同时输出 rejected；`assemble_corpus.py` 保留划分检查和图片打包；`check_student_inputs.py` 作为 export 最后一步并把 token 数写回 metadata；`calibrate_rubric.py` → verify/calibrate.py，样本来自错误注入器；`collect_validation.py` → cases/，heldout 一旦用于调规格自动降级为 dev；`rubric_r6.md` 保留为核验器的散文说明，判定规则迁到 errors.py。

扔掉：`judge_by_actor.py` 的整条轨迹一次会话评分流程；`summarize_pilot.py` 和它生成的 `试验结果.md`（被 diagnose/ 替代）；`batch_run.py`；`candidate_exclusions.json` 手写排除表（改为 verdicts 里 `disposition=negative, verifier_method=human`）；`assessment_rN[_by_actor|_sources|...]` 的目录命名和 `selected_assessment.json`。现有 826 行中 r2 评的 256 行要用新核验器重核，不能直接混入循环第 0 轮。

### 4.6 实施顺序

1. 定契约：`errors.py`、`specs/*.yaml` 格式、`episode/`、`verdicts.jsonl`、export metadata；把 rubric_r6、actor_generation_r8、actor_report_r6 和运行时角色提示拆成 `hi@0.1.0`、`gia@0.1.0`。
2. run/ 迁移：读 spec、去硬编码、教师换成 `TeacherClient`（先用本地 4B 跑通）；**解决状态渲染长度**——加 `state_renderer` 参数，让 history 压缩到 ≤8K / ≤16K 两档。在此之前不再生成数据。
3. verify/：程序性核验（E 存在、引用含实体/数字、status 与任务要求、来源键）+ LLM 逐 Finding 核验（重读 store 原文/像素）；用错误注入器校准；核验模型与教师分离。用它重核现有 826 行和各 run 的 excluded_targets，得到第 0 轮错误分布。
4. export/ + 第一次训练：只用一个 spec 版本、一个 renderer 的数据；保留 rejected；训 9B；在 heldout 上跑 gate，记录核验分↔留出提升相关性的第一个点。
5. diagnose/ + revise/：错误分布 → 修订目标 → 改 teacher_instruction / harness_params（不改 student_prompt）→ 同状态重生成对照 → 训 → gate。第一次完整循环。
6. 第二轮起加恢复轨迹和 student_prompt 修订（minor 版本），开始画错误类型曲线与方向一致率。
