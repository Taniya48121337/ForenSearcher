# 渲染档位实测：legacy / compact_8k / compact_16k（2026-09-24）

目的：为"全项目统一用 compact_16k 还是退回 compact_8k"提供数据。设计决定（2026-09-24）的门槛是 **16K 档加附图后 p95 ≤ 32K token**。

本文只报告测量结果，不做最终决定。

## 0. 测量方式

| 项 | 内容 |
|---|---|
| 数据 | `experiments/sft_data/runs/true_4124903_r1`（单个 case，2 个 HI 工作区 W1-1 / W1-2，1 轮 GIA） |
| 规格 | hi@0.2.0、gia@0.2.0 |
| 导出目录 | `experiments/sft_data/export/r0_true4124903_hi@0.2.0_gia@0.2.0_{compact_8k,compact_16k,legacy}/` |
| 计数 | `foren_searcher.datagen.check_inputs`，Qwen3.5-9B 的 processor（Qwen3VLProcessor）精确分词，文件为 hi_accepted / gia_accepted / hi_held / hi_rejected |
| 行数 | 每档 22 行：HI 20 行（accepted 17、held 2、rejected 1），GIA 2 行（PLAN 1 行、FINISH 1 行） |
| 图片 | 1280×720 一张 = 880 token；HI 与 GIA 的 `image_input_limit` 都是 8，最多 8 张 = 7 040 token |
| 分位数 | 按角色合并该角色的所有文件，用最近秩法计算（p95 取第 ⌈0.95n⌉ 个值）。与 `check_inputs.summary.json` 的逐文件分位数可能差一个名次 |
| 8k 基线 | 已有的 8k 导出用当前代码在 scratchpad 重新导出并计数，`hi_accepted.jsonl`、`gia_accepted.jsonl`、`check_inputs.rows.jsonl` 三个文件与已有文件逐字节一致，说明基线是最新的 |

**样本量警告**：HI 只有 20 行，GIA 只有 2 行，而且全部来自同一个 case。HI 的 p95 实际上是第 19 大的值。GIA 的"分位数"没有统计意义：p50 是 PLAN 行，p90、p95 和 max 都是同一行 FINISH。下面所有的 p95 都应该读成"本 run 的最大值附近"，不能当作总体分布的估计。

两个补充观察：

- 各档的名字与实际整行 token 数对不上。8k 档整行最多 16.8K，16k 档最多 20.7K。原因是 `state_render.py` 顶部写的"≈ 8K / 16K token"只按 user 消息字符估算，不含 system prompt、结尾说明和图片。另外，它假设 1 token ≈ 1.7 字符，本 run 实测为 2.2–2.7 字符/token（legacy 为 2.4–3.0），所以按字符估的 token 数偏高，偏差方向是安全的。
- 截断情况：8k 档 20 行 HI 中有 6 行带 `context_truncated`（W1-1 第 7–12 步），截断方式是丢历史步。16k 档 22 行全部未截断。

## 2. 16k 档多渲染了什么

### 2.1 Tier 参数（`src/foren_searcher/state_render.py`）

| 参数 | compact_8k | compact_16k | 作用 |
|---|---|---|---|
| budget_chars | 11 000 | 24 000 | 整个 payload 序列化后的上限（HI 的历史步也算在内） |
| latest_text_chars | 3 000 | 6 000 | 最新观察和报告里单条正文的上限 |
| history_items | 4 | 12 | 历史步 items 摘要行的条数 |
| history_excerpt_chars | 160 | 240 | 历史 READ_RECORD 的正文摘录长度 |
| list_cap | 6 | 10 | 结果列表和反馈列表的条数 |
| snippet_chars | 160 | 240 | 搜索摘要、标签等短文本的长度 |
| support_text_chars | 0 | 1 200 | GIA 报告附件 supporting_records 的正文。0 表示只留编号行 |
| report_visual_summary | False | True | GIA 是否保留每份报告的 visual_observation_summary |

`support_text_chars > 0` 还有一个连带效果：`card_line` 会给候选来源卡片附上 snippet，给证据卡片附上 `(acquired_by)`。

### 2.2 HI 实例：W1-1 第 9 步（READ_RECORD 之后决策，5 张图）

| 部分 | compact_8k | compact_16k | legacy |
|---|---|---|---|
| user 状态消息（字符） | 6 321 | 8 166 | 14 983 |
| 其中 candidate_sources（8 张卡） | 1 655 | 3 201 | 3 947 |
| 其中 evidence_view（12 张卡） | 807 | 1 113 | 2 501 |
| 保留的历史步（assistant/tool 对） | **2 / 8**（`context_truncated`） | **8 / 8** | 8 / 8 |
| tool 消息合计（字符） | 4 179 | 11 415 | 31 763 |
| 最新观察（E19 READ_RECORD 正文） | 3 974 字符，带截断标记（截到 3 000） | 6 552 字符，未截断 | 6 672 字符 |
| 文本 token | 7 458 | 10 659 | 18 549 |

这一行上，16k 比 8k 多出 3 201 个文本 token，来源分三块：

1. **历史步没有被丢掉**，约 7K 字符。8k 档预算不够，丢掉了 6 个历史步，只剩 SEARCH(video) 和最后一步 READ_RECORD(E19)。16k 档保留了全部 8 步：INSPECT get_frames、两次 SEARCH（10 条和 5 条 items 摘要）、E11/E16/E12 三次 READ_RECORD（各 240 字符摘录）。
2. **最新观察正文从 3 000 字符放宽到 6 000 字符**。E19 从截断变成完整。
3. **卡片变成带摘要的长行**，约 1.9K 字符。8k 档的候选卡是 `R8 page: — 标题 — URL`，16k 档在后面再附上 240 字符的搜索摘要，证据卡加上 `(SEARCH/open/…)`。

HI 其他行（没有触发 8k 截断的行）多出的量主要来自第 3 块，另有部分来自历史 SEARCH 的 items 摘要行（4 → 12 条），每行多 +850 到 +1 450 token。

### 2.3 GIA 实例：FINISH 行（8 张图，2 份 HI 报告）

| 部分（global_view） | compact_8k | compact_16k | legacy |
|---|---|---|---|
| user 状态消息（字符） | 10 685 | 23 162（**预算的 96.5%**） | 39 650 |
| latest_reports | 5 571 | 17 454 | 30 286 |
| 其中 supporting_records（11 条 + 8 条） | 730 + 749（每条一行） | 6 237 + 5 252（每条带 ≤1 200 字符正文） | 15 447 + 8 660 |
| 其中每份报告的 image_inputs | 833 + 543（只留编号/定位） | 1 326 + 631（完整） | 同 16k |
| 其中每份报告的 visual_observation_summary | 删除 | 718 + 514 | 同 16k |
| current_materials | 1 950 | 2 526 | 5 151 |
| 文本 token | 9 754 | 13 667 | 19 675 |

GIA 多出来的 token 几乎都在 latest_reports 里，主要是 supporting_records 的原始正文页。8k 档每条是 `E16 [text] Smoke rises around Eiffel Tower ← R11` 这样的一行。16k 档是 `{evidence_id, modalities, label, source_ref, acquired_by, locator, content(≤1 200)}`。其次是各报告的视觉摘要和完整附图记录。

## 3. 训练配置与截断

`training/configs/hi_r0.json` 和 `gia_r0.json`：

- `max_tokens: 32768`。`training/sft_lora.py` 不截断序列：整行超过 `max_tokens` 就跳过并计数（`encode` 返回 None），损失只算最后一条 assistant。因此**不会出现"截掉监督目标之前的上下文、但保留目标"的情况**。超长行会整行丢失，而不是被静默截断。
- 本 run 三档都没有行超过 32 768，所以 16k 档没有行会被跳过（legacy 也没有）。`check_inputs` 的 `too_long` 在三档中都为空。
- **需要注意的配置问题**：两份 config 的 `export_dir` 仍指向 `r0_true4124903_hi@0.1.0_gia@0.1.0_compact_8k`，也就是旧规格加 8k 档。如果统一用 16k，这里需要改到对应的 16k 导出目录。本次任务不改源码和配置，只记录这一点。
- 16k 档的理论上限（用来判断以后更大的 run 会不会超）：
  - payload 被渲染器限制在 24 000 字符以内。超出时渲染器先按规则丢内容，丢完仍超则抛出 `RenderError`。
  - 预算之外的文本有两部分：system prompt（HI 3 846 字符，GIA 5 058 字符）和结尾说明，本行的结尾说明为 HI ≈2.2K 字符、GIA ≈5.3K 字符。
  - 按保守的 1.7 字符/token 计：GIA 约 (24 000 + 5 058 + 5 300) / 1.7 ≈ 20.2K，加 8 张图 7 040，约 27.2K。HI 约 (24 000 + 3 846 + 2 500) / 1.7 ≈ 17.9K，加 7 040，约 24.9K。
  - 按实测的 2.2 字符/token 计：分别约 22.7K 和 20.8K。
  - 两种算法都低于 32 768。前提是图片仍为 1280×720 且每次最多 8 张。

## 4. 结论

### 4.1 是否满足 p95 ≤ 32K

数据显示，compact_16k 加附图后，HI 的 p95 是 15 059（max 16 221），GIA 的 max 是 20 707，全部行都在 32 768 以内，余量至少 12K token。若按决定的门槛（16K 档加附图后 p95 ≤ 32K），本 run 满足。

但样本只有 22 行、1 个 case，GIA 只有 1 行 FINISH，p95 实际上就是 max，不能代表总体。支撑这个结论的更有力依据是第 3 节的结构性上限：渲染器预算加 8 张图的上限，按保守的 1.7 字符/token 估算约 27K，仍在 32K 以内。这个上限不依赖样本量，但依赖三个前提：图片尺寸不变、`image_input_limit` 不变、system prompt 和结尾说明不明显变长。

### 4.2 GIA FINISH 这种带 8 张图的行在哪档最危险

数据显示，GIA FINISH 在每一档都是最长的行：8k 为 16 794，16k 为 20 707，legacy 为 26 715。

- **legacy 最危险**：没有预算，latest_reports 随报告数和 supporting_records 条数线性增长。本 run 只有 2 份报告就已经 26.7K，离 32K 只差约 6K。多一两个工作区，或者多一轮 memory_history，就会超过 32K，训练时整行被跳过。
- **16k 档对长度是安全的，但对内容处在临界状态**：本行 payload 已经用了 24 000 字符预算的 96.5%。报告再多一些，`_fit_gia` 就会开始先丢 memory_history、再压缩 supporting_records 的正文（1 200 → 600 → 300 → 150）、最后把附图记录只留编号。也就是说，16k 档把风险从"整行超长"变成了"GIA 看到的正文变少"，token 数本身有上限保证。
- 8k 档对 GIA 长度最安全，但 supporting_records 本来就只有编号行，GIA 看不到正文，只能靠 READ_RECORD 补读。

### 4.3 建议与依据

数据倾向于支持统一用 compact_16k。依据如下：

1. **门槛**：本 run 的 p95 和 max 远低于 32K，结构性上限按保守算法也约 27K，不超过 32K。若按决定的门槛，16k 满足条件，不需要退回 8k。
2. **代价小**：16k 相对 8k，HI 文本平均多 15.6%（中位数每行 +899 token），GIA 多 34%。加上图片后，HI 的 p50 从 10.0K 到 11.3K，增幅约 12%。
3. **信息收益集中在 8k 丢得最多的地方**：
   - 8k 档有 30% 的 HI 行（6/20）靠丢历史步才塞进预算。W1-1 第 9 步 8 个历史步只剩 2 个，而且最新读取的 E19 正文被截断。16k 档没有一行被截断。
   - GIA 在 8k 档完全看不到 supporting_records 正文，16k 档能看到每条最多 1 200 字符。
   - 这些正是 SFT 教师轨迹中模型做决策时实际依赖的上下文。训练时看到的上下文比教师当时看到的少，会造成训练与部署不一致。

若采用 16k，建议同时跟进四件事：

- 把 `training/configs/*_r0.json` 的 `export_dir` 改到 hi@0.2.0 / gia@0.2.0 的 16k 导出目录。
- 在更多 case 和多轮 run 上重跑本测量，并单独统计 GIA FINISH / INVESTIGATE 行的 `context_truncated` 比例。对 16k 来说，风险在内容被截，而不在超长。
- 部署端的 `max_model_len` 至少为 32K，并为生成留出余量。
- 如果以后放宽 `image_input_limit` 或提高图片分辨率，重新核算第 3 节的上限。
