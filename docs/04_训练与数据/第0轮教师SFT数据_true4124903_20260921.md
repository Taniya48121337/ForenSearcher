## 四、诚实的边界

1. **answer 单元的锚定是代理 → 代码已就位，等本机跑**。云端连不上 OpenRouter，当前导出仍是 `anchored_method: proxy_report_judgments`。`verify/answer_anchored.py` 已写好：把答案按句拆（"（E24、E21）"一组引用覆盖它前面到上一组引用为止的同段句子；只引 F 的句子换成该 Finding 的 E），拼成伪报告走第二层"部分支持 + 覆盖汇总"，写回 answer 单元（`anchored_method: judge_sentences`，proxy 的 flag 错误被替掉、处置重算）。本 run 的答案拆成 7 句、0 句无引用。
2. **plan 单元的缺口评判是 hindsight → 加了模型评判，与 hindsight 并列**。`verify/plan_judged.py` 让核验模型只读任务文字 + 案卷 REQ + 本轮前已覆盖集合 + GIA 视图里的既有报告摘要，给每个任务的 targets / gap_driven / premises（given_in_case | verified_earlier | unverified）。`gap.judge_targets` 与 `gap.task_targets`（hindsight）并存并记 `agreement`；全部目标已覆盖 → `task_not_gap_driven`（major），unverified 前提写成事实 → 新增错误类型 `premise_smuggling`（major，传播）。gap 仍只进 metadata（v2 §2.4）。
3. **校准是规则版 → 召回率校准代码就位**。`verify/calibrate_recall.py`：对判定干净的 Finding 做六种注入（换引用 swap_citation、追加编造句 append_clause、数字 +13 alter_number、去掉"据 X 称" drop_attribution、追加不存在的 E fabricate_id、删必需 Finding 仍报 COMPLETED drop_required_finding），每种事先知道该报什么错，用同一条 `verify_report` + 同一缓存重核，出 by_kind / by_expected_type 召回率与漏报清单。假核验模型下四种主要注入召回 1.0、只跑程序层时 fabricate_id 1.0 / append_clause 0.0（符合预期）。真实召回率要等本机跑；在那之前 negative 报告仍标 `negative_report_until_recall_calibrated`。
4. **system 与运行时不完全一致 → 已解决（HI）**。发了 `specs/hi@0.2.0`（parent 0.1.0，minor，changelog targets completed_without_finishing / empty_report）：student_prompt = 0.1.0 + 运行时 `_hi_turn_prompt` 追加的时间预算附注，`validate_bump` 通过。重导出后 `runtime_system_matches_spec` HI 20/20 True；GIA 仍 1 True 1 False（主提示与规格差异留给 gia@0.2.0）。
5. **训练冒烟不是训练**。`--smoke-tiny` 用同架构（Qwen3_5ForConditionalGeneration，线性/全注意力交错、视觉塔）的 64 维随机模型，取前 512 token 跑一步，证明的是"取数据 → 编码 → 加权损失 → 反向 → 存 LoRA → 加载 → 前向"这条链能走通；loss 数字无意义。真实训练要在 5090（4B）或服务器（9B）上用 `training/configs/*.json` 跑，CPU 环境装不下权重。
6. **只有一个 run**。19 行 HI、2 行 GIA 训不出任何东西；这是流水线的验证，不是数据集。下一步是把 bridge 模式的其余 5 个 run（true 3 个、videosham 2 个）各写案卷后用同一条命令导出，hi 模式 run 的 HI 部分同理（GIA 行自动跳过），GIA 再靠来源 D 补。

## 六、接核验模型的三件事（2026-09-21 晚）

| 事 | 模块 | CLI | 产物 | 写回哪里 |
|---|---|---|---|---|
| answer 逐句锚定 | `verify/answer_anchored.py` | `verify.complete_units` | `verdicts_units_judged.jsonl`（answer 单元） | `extra.anchored.method=judge_sentences`、`sentences[]`、`unsupported_sentences`、judgments / coverage、处置重算 |
| plan 模型评判 | `verify/plan_judged.py` | 同上 | 同上（plan 单元） | `extra.gap.judge_targets / agreement`、`extra.checks.premises`、`task_not_gap_driven` / `premise_smuggling` |
| 召回率校准 | `verify/calibrate_recall.py` | 本身 | `calibration/recall_r0.json` | 只出报告；下一版 verifier 据此改规则或提示 |

`export --units <jsonl>` 把前两者叠加到程序层的 verify_units 结果上（按 run + request + unit 匹配）；manifest 记 `units_source`；行 metadata 多了 `unsupported_sentences`、`premises`、`plan_judged`。

**为什么要本机跑**：云端环境到 openrouter.ai 的连接被出口策略拒绝（403 CONNECT），且本机 `.local/openrouter.json` 里的密钥是 Windows DPAPI 加密的，只有本机能解。`补全核验_本机跑.cmd` 四步：complete_units → calibrate_recall → export（hi@0.2.0 + --units）→ check_inputs。核验模型仍是 `qwen/qwen3.8-27b`（与教师 gpt-6-astra 不同），`--reasoning low`。

**跑完要看的三个数**：answer 单元 `unsupported_sentences` 是否为空（不为空则 GIA 那行从 accepted 掉到 held / rejected）；plan 单元 `agreement` 里 judge 与 hindsight 是否一致（不一致的先信 judge，因为 hindsight 会把"派对了没办成"算成没对准）；`recall_r0.json` 的 by_kind——哪种注入抓不住，就是 verifier@0.3.0 要修的地方。

### 本机跑完的结果（2026-09-21 深夜，qwen/qwen3.8-27b，reasoning low）

**answer 逐句锚定**：7 句 × 13 对，全部有判定、0 pending（帧 E3/E7 用 request 附图补了像素）。覆盖层 7 句全部 grounded，
`unsupported_sentences=[]`。唯一的错：A3「随后明确确认这是意外火灾，已经扑灭，埃菲尔铁塔本身没有着火」被 E24 判 contradicted
（E24 是警方第一条推文"卡车起火、消防员出动"），但同句所引 E21（第二条推文）逐字支持"已经扑灭"。这是逐对核验的固有盲区
（一次只看一条 E，把"更早的状态"当成"相反"），不是教师错——教师引两条推文本来就是在引前后通报。于是加了校准规则
**R4 contradiction_covered_by_sibling**（calibrate@0.3.0）：同句另一条被引 E 有核实的支持片段覆盖同一部分时撤销反驳；
recalibrate 现在也处理 answer 单元，`export --units` 叠加时自动过。校准前 FINISH 行掉进 gia_rejected，校准后回到 accepted（权重 2），
剩一条 minor scope_overreach。

**plan 模型评判**：T1→{REQ2,REQ3}、T2→{REQ1,REQ2}；与 hindsight 的差别只在 T1 少了 REQ1（hindsight 因为 W1-1 的 Finding 引了警方通报
把 REQ1 也算给 T1，judge 按任务文字判 T1 是"查来源与语境"）——judge 更准。前提：T2 的「相关火情原因及是否涉及恐怖袭击的记载」
判 given_in_case（原始声明本身就说了铁塔附近有火），无 unverified；无 premise_smuggling。处置 positive 不变。

**召回率校准**（19 处注入，六种；与基线同条件即不带案卷，2026-09-23 重跑）：
内容类四种注入 **15/15 全中、零假命中**——swap_citation 4/4（连第一次漏掉的 F5 换 Snopes/纽约每日新闻也抓到了，
不带案卷后充分性层不再干扰，逐句覆盖判定把"警方通报""耶拿桥"这些部分判成了无支持）、fabricate_id 4/4、
append_clause 4/4、alter_number 3/3；drop_attribution 0 处（本 run 没有"据 X 称"句式，注不进去）。
唯一的系统性漏报是 **drop_required_finding 0/4**：删掉一条 Finding 仍报 COMPLETED，不带案卷时充分性层只看任务文字，
剩下的两三条 Finding 照样"回答了局部任务"，判 COMPLETED 无误——这不是模型漏看，是没有案卷它就没有"该拿的清单"。
带案卷跑（第一次）它 4/4 全中，但代价是每处注入都多一条假的 omitted_required_fact，因为整案的 required_evidence 被压到了
单个工作区头上。两次结果合起来就是 verifier@0.3.0 要改的地方：充分性层要拿到的是**这个工作区的任务对准的那几项**要求
（plan 评判的 judge_targets → requirements → required_evidence.supports 反查），而不是整案清单，也不是什么都没有。
总召回 15/19 = 0.789 这个数本身没意义，按类看才有：文本内容错误的召回是 1.0，状态级错误在当前条件下不可测。

**未做**：GIA 主提示与规格的差异（gia@0.2.0）；sufficiency 层改成"只要求本工作区任务对准的那几项"（verifier@0.3.0，
上面召回结果的直接结论）；召回校准目前只在 report 单元上注入，answer 单元的逐句锚定还没有对应的注入；plan 评判的 premises 规则没有召回校准。
