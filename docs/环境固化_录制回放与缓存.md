# 环境固化：检索录制回放、工具结果缓存、规格参数生效

目的：同一个案例在不同臂、不同轮次重跑时，模型看到的是同一个世界。差异只应来自被比较的那个改动，不应来自：

- 开放网络漂移，比如搜索排序变了、页面改了、视频下架、限流时有时无（由**检索录制回放**解决）；
- 工具本身的不确定性，比如 OCR 或 ASR 两次结果不同、对齐锚点抖动（由**工具结果缓存**解决，并用**重跑方差报告**量化它有多大）；
- 规格版本与实际参数对不上（由 **harness_params 生效**解决）。

三件在默认参数下都不改变旧行为：`--search-mode live`、`--tool-cache off`。`--harness-params apply` 是默认值，
但默认规格（hi@0.3.0 / gia@0.4.0）与服务器配置完全一致；在本机 `configs/local.toml` 下只有一处差异，见第 3 节。

## 1. 检索录制回放（`search/recording.py`）

### 用法

```bash
# 第一次：联网并录下整个检索世界
python -m foren_searcher.datagen.run_cases --round r1 --search-mode record
# 对照臂、重跑：只读快照，不联网；快照里没有的请求报 replay_miss
python -m foren_searcher.datagen.run_cases --round r1b --search-mode replay
# 边跑边补：命中就回放，未命中就联网并补录
python -m foren_searcher.datagen.run_cases --round r1c --search-mode replay_or_record
# 快照在别处
... --snapshot-root D:/snapshots
# 看快照：条目数、大小、漂移、各 run 的命中率
python scripts/snapshot_stats.py [--case true:4124903] [--json]
```

| 模式 | 行为 |
|---|---|
| `live`（默认） | 不包装，与以前完全相同 |
| `record` | 照常联网，每次结果写进快照。同一个 key 后写的覆盖先写的；内容指纹没变就不重复写 |
| `replay` | 只读快照。未命中就抛 `ReplayMiss`（SearchFailure，错误码 NOT_FOUND，reason 是 `replay_miss`），写日志，**绝不联网** |
| `replay_or_record` | 命中就回放，未命中就联网并补录。录下的瞬时失败（TIMEOUT / NETWORK_ERROR / PROVIDER_ERROR / RATE_LIMITED）当作未命中，会重新联网 |

### 录什么

| kind | 包在哪 | 录的内容 |
|---|---|---|
| `search` | SearchService.provider | 每次 `provider.search` 返回的 CandidateBatch：候选的全部字段、raw_response、request_metadata。provider 抛出的 SearchFailure 也录 |
| `open` | SearchService.opener（SourceDispatcher） | 每次打开得到的 OpenedSource 全部字段：final_url、每份材料（正文 content、字节 artifact_bytes、media_type、suffix、label、locator、error……）、download_check、video_material、discovered_links。打开失败也录 |
| `acquire` | InspectService.acquirer（DirectMediaAcquirer） | INSPECT 受控获取下来的视频文件（直链或 HLS），以及 AcquiredMedia 的元数据 |

视频文件是在 INSPECT 里下载的，不经过 SEARCH 的 opener。只录 SEARCH，回放时视频仍会联网，所以 acquirer 也一起包。

### 与护栏、案卷过滤的顺序

由内到外依次是：真实 provider/opener、录制回放、案卷过滤（exclude_original / source_bound）、检索护栏。也就是
`guard(filter(replay(base)))`。快照里存的是**原始世界**，包括核查站点和晚于截止日的来源。黑名单和日期截断在回放时照常生效，
所以换护栏参数（`--blocklist mark|off`、`--date-cutoff`）不需要重新录制。

### 目录结构（按 case_id 共享，不按 run 分）

```
experiments/sft_data/search_snapshots/          ← --snapshot-root（已在 .gitignore）
  true_4124903/                                 ← case_id 里的非法字符替换成 _
    index.jsonl                                 ← 一行一条，同一个 key 以最后一行为准
    blobs/ab/ab12…（sha256）                    ← 正文、原始响应、材料字节、视频文件，按内容去重
    usage/true_4124903_r1_1.json                ← 每个 run 结束时写的命中 / 未命中 / 新录计数
```

`index.jsonl` 每一行的字段：`format, kind, key, request（规范化后的请求，便于人读）, outcome（ok|failure）, transient, payload,
fingerprint, run, recorded_at`。超过 2 KB 的文本进 blob，每一行因此保持较短。多个进程同时追加时，POSIX 下用 flock 加锁，
Windows 下用 msvcrt 加锁。

run 目录下另有 `search_snapshot.jsonl`：记录未命中（replay_miss / miss_recorded_live）和漂移（drift，即同一个 key 重录后内容变了）。

### 请求规范化（key 的稳定性）

- **查询**：`input_type, output_type, offset, limit`，加上 NFC 规范化并折叠空白后的查询文本。图片查询**不用 E 编号**，因为每个 run 的编号可能不同，
  改用上传给 provider 的 JPEG 字节的 sha256。
- **打开**：规范化 URL，包括主机名小写、去掉默认端口和 fragment、去掉 `utm_*`、`fbclid`、`gclid`、YouTube `si=` 这类随机追踪参数，并给查询参数排序。
  再加上候选类型、图片 / 缩略图 URL、平台和视频 ID、Service 注入的"已缓存材料"列表、输出类型、请求种类（查询时打开还是直接打开）、字幕选项。
  **候选的标题、摘要、排名、extra 不进 key**，因为它们随 provider 响应变化。
- **视频获取**：规范化后的直链。签名直链只要来自回放出来的元数据，就与录制时逐字相同。
- **内容指纹**：先去掉时间戳、请求 ID、耗时、`search_metadata` 这类易变字段，再算 sha256。指纹只用来判断"重录时内容是否真的变了"，
  也就是统计漂移，并在内容没变时跳过写入；它不影响回放。

### run_config 字段

```json
"search_mode": "replay",
"search_snapshot": {
  "search_mode": "replay", "snapshot_root": "experiments/sft_data/search_snapshots",
  "snapshot_dir": "experiments/sft_data/search_snapshots/true_4124903", "case_key": "true_4124903",
  "counts": {"hit": 14, "miss": 1, "recorded": 0, "recorded_unchanged": 0, "live_calls": 0},
  "by_kind": {"search": {"hit": 4}, "open": {"hit": 10, "miss": 1}},
  "hit_rate": 0.9333
}
```

run 开始时先写一次（计数为 0），run 结束（包括异常退出）时在 `finally` 里用最终计数再覆盖一次。批量成本记录
`run_manifests/<轮次>.jsonl` 每行也带 `search_mode` 和 `search_snapshot` 计数。

## 2. INSPECT 工具结果缓存（`inspect/tool_cache.py`）

### 用法

```bash
python -m foren_searcher.datagen.run_cases ... --tool-cache on          # 命中复用，未命中算完写入
python -m foren_searcher.datagen.run_cases ... --tool-cache refresh     # 一律重算并覆盖（换了模型或权重之后用）
python -m foren_searcher.datagen.run_cases ... --tool-cache-root D:/tool_cache
```

### 落在哪一层，为什么

缓存包在 **Processor 层**，也就是 `InspectDispatcher.processors[op].process(media, params, policy, query_media)` 这一层：

- 这一层是纯函数：输入是已经解析到本地文件并 probe 过的媒体、强类型参数和 InspectPolicy；
  输出是 `BackendOutcome`，包含结果字典、内存中待提交的图片、问题和诊断。它**不访问 Store，也不分配 E 编号**。
- 分配 E 编号、提交 Artifact、复用帧和页（`_reusable_media_image`）、写结构化结果 E，这些都在 `InspectService` 里完成，
  时间点是 processor 返回之后。缓存命中后仍走这条正常路径，所以证据记录的 `derived_from`、`locator`、`production_method`、`content`、
  图片字节都与未命中时一致，唯一的区别是 BackendOutcome 从缓存来。测试 `test_cache_hit_keeps_evidence_shape_and_normal_id_allocation` 逐字段比较了两者。
- 放在更低一层（backend 里单次 RapidOCR / Whisper 调用）粒度太细：一次视频 OCR 要调几十次引擎，而且中间的抽样决策也会漂。
  放在更高一层（`InspectService.execute`）则已经写过 Store，缓存它就等于缓存 E 编号；不同 run 的编号不同，证据闭包会出错。
- 同一 run 内，Service 已有 `_completed_requests` 按请求复用结果；本缓存管的是跨 run、跨臂的复用。

### key 与 value

key 由以下部分的 sha256 组成：

- 操作名；
- 每个输入媒体文件的 sha256 和媒体类型；
- 规范化参数；
- 影响输出的 InspectPolicy 字段（不含超时、线程数、大小上限这类资源保护字段）；
- 后端和模型标识：后端类名、该操作读取的模型环境变量（`FOREN_WHISPER_MODEL` / `FOREN_WHISPER_DEVICE` / `FOREN_VLM_MODEL` / `FOREN_CLIP_MODEL` / `FOREN_GROUNDING_MODEL` / `FOREN_AUDIO_MODEL`），
  以及相关包的版本（rapidocr、onnxruntime、faster-whisper、ctranslate2、av、numpy、Pillow、opencv、PyMuPDF、transformers、torch……）。
  后端如果实现了 `cache_identity(operation)`，其返回值也并入 key。

**E 编号的处理**：

- visual_qa / audio_qa 的提示词里含 E 编号和来源上下文，所以这两项进 key。
- 其余操作的输出里，E 编号只出现在结构位置：`PendingArtifact.parent_evidence_id`、标签（如"视频E3在1.000秒的帧"）、`image_evidence_id(s)`。
  写缓存时把它们换成 `⟦media0⟧` 这样的占位符，命中时再换回本次调用的编号。因此同一个媒体在不同 run 里编号不同，也能命中。
- OCR / ASR 识别出的文字不做替换。

value 包括结果 JSON、issues、details，以及产出文件（帧、页、裁剪图），文件按 sha256 去重存进 blobs。

**只缓存确定的结果**：抛出 BackendFailure 的调用不缓存；outcome 里只要有一个 `retryable=True` 的问题（例如某一帧解码失败）也不缓存，下次还有机会算完整。

### 目录结构

```
experiments/sft_data/tool_cache/                ← --tool-cache-root（已在 .gitignore）
  entries/3f/3f9a…json                          ← 一次调用：key_material（可读的 key 组成）、result、artifacts、issues、details、elapsed_s
  blobs/ab/ab12…                                ← 产出的图片
```

### run_config 字段

```json
"tool_cache": {"mode": "on", "root": "experiments/sft_data/tool_cache",
               "counts": {"hit": 5, "miss": 2, "stored": 2, "refreshed": 0, "not_cacheable": 0, "corrupt": 0},
               "by_operation": {"ocr": {"hit": 3}, "get_frames": {"hit": 2, "miss": 2, "stored": 2}},
               "hit_rate": 0.7143, "saved_seconds": 41.3}
```

每次 INSPECT 执行审计的 `details.tool_cache` 也带 `{"status": "hit|miss|refresh", "key": …}`，命中和未命中都带，形态一致。
结果 E 的 content 只读取 details 里的固定几个键（backend、model……），不读 `tool_cache`，所以证据内容不受影响。

### 重跑方差报告（`scripts/tool_cache_variance.py`）

```bash
python scripts/tool_cache_variance.py --media A.mp4 --operation ocr --runs 5 --out variance_ocr.md
python scripts/tool_cache_variance.py --media A.mp4 --operation asr --params "{\"language\": \"en\"}" --runs 3
python scripts/tool_cache_variance.py --media A.mp4 B.mp4 --operation align_media --params "{\"mode\": \"visual\"}"
python scripts/tool_cache_variance.py --media A.mp4 --operation get_frames --params "{\"count\": 8}" --fresh-backend
```

直接调用 processor 层（不包缓存、不经过 Store），重跑 N 次，所有指标都相对第 1 次运行计算：

| 操作 | 指标 |
|---|---|
| ocr / asr / visual_qa / audio_qa | 文本相似度（`difflib.SequenceMatcher` 比例，1.0 表示逐字相同） |
| align_media | 最佳匹配的锚点差（秒；每个锚点取 time_b − time_a，再取中位数，比较这个中位数的差）；候选区间 IoU（A、B 两侧取平均） |
| get_frames / get_pages / crop | 解码后 RGB 像素的哈希是否一致（PNG 编码不同但像素相同也算一致） |

加上 `--fresh-backend` 后，每次重跑都新建后端，模型加载本身的不确定性也会被计入。输出是 markdown 表。

## 3. 规格 harness_params 生效（`datagen/harness_params.py`）

### 映射表

| 键 | 运行时位置 | 归属 | 范围 | 状态 |
|---|---|---|---|---|
| `image_input_limit` | `InspectPolicy.maximum_visual_qa_images`：INSPECT 服务，以及教师的 `image_policy` | 共享 | 1–64 | 已接线 |
| `max_workspace_turns` | `InvestigationRuntime(max_workspace_turns=…)`，覆盖 `[runtime]` | HI | 1–200 | 已接线 |
| `read_page_chars` | `MemoryPolicy.max_read_chars` | 共享 | 200–1,000,000 | 已接线 |
| `max_model_view_chars` | `MemoryPolicy.max_model_view_chars` | 共享 | 4,000–4,000,000 | 已接线 |
| `max_evidence_cards` | `MemoryPolicy.max_evidence_cards` | 共享 | 1–1,000 | 已接线 |
| `max_candidate_cards` | `MemoryPolicy.max_candidate_cards` | 共享 | 1–1,000 | 已接线 |
| `state_renderer` | `MemoryPolicy.state_renderer`，写入 `runtime_constraints.state_renderer` | 共享 | legacy / compact_8k / compact_16k | **部分生效**：本地学生（local_models）和导出会按档位渲染；EndpointTeacher / Codex 教师**不**按档位渲染输入 |

没有"完全未接线"的键：规格里现有的 7 个键在运行时都有对应参数。

### 规则

- `--hi-spec` / `--gia-spec` 选中的两份规格的 harness_params 会覆盖运行时配置。默认配置是接线前 run_cases 实际使用的那一套：
  `configs/*.toml` 的 `[runtime]`（没有配置文件时用内置默认），加上 `MemoryPolicy()` 和 `InspectPolicy()`。
- **未知键直接报错**。`Spec.load` 本来就会拒绝未知键；映射层对绕过 Spec 的输入同样报错。`specs.DEFAULT_HARNESS_PARAMS`
  新增的键如果没写映射，也会报错，不会出现"记了但不生效"。
- **类型和范围**：按上表校验；bool 不能当 int 用；Policy 自身的 `__post_init__` 再做一层兜底校验。
- **两份规格冲突**：运行时只有一份 MemoryPolicy / InspectPolicy，共享键在两份规格里取值不同就报错。
  只属于 HI 的键（`max_workspace_turns`）取 HI 规格的值；GIA 规格里的同名值记入 `not_applicable`。
- 主进程在开跑前（`--dry-run` 也一样）先解析一次，打印与默认配置不同的项。出错就在这里停下，不会让每个子进程各报一次。
- `--harness-params record`：只校验和记录，不覆盖，也就是旧行为，用于对照。

### run_config 字段

```json
"harness_params_applied": {"max_workspace_turns": {"value": 12, "source": "hi@0.3.0", "target": "runtime.max_workspace_turns"}, …},
"harness_params": {
  "mode": "apply", "applied": {…},
  "not_applicable": {"max_workspace_turns": {"value": 12, "source": "gia@0.4.0", "reason": "…只作用于 HI…"}},
  "differences_from_default": {"max_workspace_turns": {"target": "runtime.max_workspace_turns", "default": 8, "spec": 12,
                                                       "source": "hi@0.3.0", "effective": 12}},
  "unwired": []
},
"harness_param_map": [...映射表...],
"effective_settings": {"runtime": {...}, "memory_policy": {...}, "inspect_policy": {...}},
"runtime_limits": {...覆盖后的 [runtime]...}
```

### 与旧行为的差异

- 服务器配置（`configs/server.toml`）加默认规格：**没有差异**。
- 本机配置（`configs/local.toml`）加默认规格：`max_workspace_turns` 从 8 变为 12，因为规格值覆盖了本机调试配置。
  如果要保持本机的 8，可以用 `--harness-params record`，或发一个把 max_workspace_turns 设为 8 的规格版本。
- `configs` 里的 `[runtime].state_renderer` 以前和现在都**不被** run_cases 使用（只有 demo 用）。run_cases 用的是规格的 `state_renderer`。

## 局限

1. **回放未命中会进入模型观察**。replay 模式下，未命中在模型看来是 NOT_FOUND 错误，消息里带 `replay_miss`。
   严格对照时应先用 record 或 replay_or_record 把世界录全，再用 replay 跑各臂；用 `snapshot_stats.py` 检查命中率，
   把含未命中的 run 从训练数据里剔除，或单独标注。
2. **快照是"模型问过的"世界，不是整个网络**。不同臂问出不同查询时，replay 会未命中，replay_or_record 会在录制时刻补录。
   后一种情况下，两臂看到的世界在时间上不完全同步，漂移会记在 `search_snapshot.jsonl` 的 drift 行里。
3. **provider 的身份不进 key**。换搜索后端（DDGS 与 SearXNG）后，回放仍会返回旧后端录下的结果；这是有意的，快照代表"这个案例的世界"。
   如果要比较 provider 本身，请用不同的 `--snapshot-root`。
4. **打开动态页（Playwright）** 与静态打开共用同一个 key，但 run_cases 目前不开启动态页。
5. **工具缓存的模型标识是环境变量里的模型名或路径**。同一路径下替换了权重文件，不会自动失效，需要用 `--tool-cache refresh`，
   或让后端实现 `cache_identity()` 返回权重哈希。
6. **只缓存确定的结果**。带可重试问题的结果不缓存，所以在不稳定的媒体上缓存命中率会偏低。
7. **视频快照体积**。视频文件按内容去重，但仍可能很大（单个上限 384 MB）。快照目录已在 .gitignore 里；如需备份，请单独归档。
8. **Windows 上的并发追加**依赖 `msvcrt.locking`。同一案例多个 sample 并行做 record 时，同一个 key 以最后写入的为准；
   这不会损坏快照，但"谁的版本留下"没有保证。

## 6. 对照实验用的临时参数覆盖与"搜索附摘录"（2026-09-30）

- `run_cases --harness-override 键=值 ...`：临时覆盖规格里的 harness_params，优先于规格，按映射表校验类型与范围，
  来源记为 `override`，run_config 另记 `harness_overrides`。试出来有效再发规格新版本；不要把 override 跑出来的数据当作某个规格版本的数据。
- 新参数 `search_excerpt_chars`（只作用于 HI，默认 0 = 关）：SEARCH 自动打开网页后，观察里给每页附一段与查询词重合最多的连续句子
  （纯程序挑选，不调模型），并注明"完整正文用 READ_RECORD"。摘录不算已读正文（content_observed 不变）。
  目的：检验"少一步 READ_RECORD"是否让 HI 更多地去搜、读到更多独立来源。对照脚本：`scripts\_机制对照_摘录与附图上限.cmd`。
- 同一脚本的 B 组把 `image_input_limit` 临时调到 16，看 4126 这类精细定位任务的连续抽帧步数是否下降。
