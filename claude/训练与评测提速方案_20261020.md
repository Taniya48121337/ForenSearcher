## 〇、先看这里

1. **服务器 GPU 在持续热降频，这是训练 MFU 低的最大单项原因。** 训练进行中（00:48–01:00 UTC）实测：`Clocks Event Reasons: SW Thermal Slowdown: Active`，计数器 704 s 里涨了 632 s（**90% 的时间在热降频**），GPU 86–91 °C（T.Limit 余量 -1 °C），**SM 时钟平均 858 MHz、中位 675 MHz，上限 1785 MHz**。按这个时钟，卡实际能给的峰值只有标称的 ~48%。同期训练 1.0–1.09 ms/token（step 1→10：873,680 token / 953 s）。修好散热（或换一台不降频的机器）预计训练 **×1.3–1.7**，单种子 HI + GIA 约省 **6–9 h**；不改任何数值。**负责人 10-20 定：随 4×H200 迁移换掉这台，新机器只收通过 10 分钟烧机准入（`server/29_burn_in.sh`，六节 G0）的。**
2. **按 FLOPs 重算：软件栈本身没那么差。** 每 token 硬件 FLOPs ≈ 6 × 24.3 B（不含词表 / 视觉塔的矩阵参数）+ 注意力 ≈ 155 GFLOP；1.05 ms/token → 148 TFLOPS。对 H200 NVL 标称 bf16 稠密峰值 835 TFLOPS 是 18%；对 858 MHz 下的实际峰值（~400 TFLOPS）是 **~37%**——剩下的软件空间是 1.3–1.5 倍量级（检查点粒度、torch.compile、每行 CPU 预处理），不是 3–5 倍。
3. **评测不是被"并发不够"卡住，而是每次调用在负载下又慢又长。** 1,960 次调用：输出 ≤ 40 token 的调用（≈ 只有排队 + prefill）负载下中位 **8.2 s**；~1K token 输出的调用中位 75 s（≈ 67 ms/token，单跑约 11 ms/token）。模型等待总量里 **≈ 62% 是 decode、38% 是首 token 前**。前缀缓存命中只有 **26%**（= 系统提示那一段）：图片（占输入 40–43%）放在每轮都变的状态 JSON 之后，永远命中不了，尽管其中 82% 的图片 token 上一轮刚发过。
4. **这轮就能做的评测项**：MTP 投机解码（底座带 MTP 头：权重里 15 个 `mtp.*` 张量，vLLM 0.32 有 `qwen3_5_mtp.py`）、并发 12 → 24 同时把 `--max-num-seqs` 从 16 提到 ≥ 32（**现在 16 是并发 24 时的硬上限**）。两项都先用回放压测定量（G4），再上。预计评测 3 h → 1.5–2 h。
5. **否掉的假设**：跨种子工具缓存（两个种子之间打开 / 下载的同一 URL 只有 4 / 607、4 / 110，<1%，不用做）；训练 micro-batch 1 的 kernel launch 开销、padding（batch 1 没有 padding）、训练进程的 CPU 线程上限（`/proc/<pid>/environ` 里没有 OMP / MKL 限制）都不是主因。flash-attn2 变体"快 20%"不是 sdpa 慢的证据（它的 loss 全 nan，很可能算的是错的东西，见二节 T6）。
6. 另两个对话已经在做 / 做完的，本文不重复：prescan 缓存（`e3f9e6c`，已提交）、`runtime.mixed_precision`（未提交，`server/27_mp_check.py`）、accelerate DDP（4×H200）、profiler 分层计时（`server/26_profile_step.py`，结果等转来再并进二节）。

## 二、训练：为什么只有 15–20% MFU（问题 ① ②）

FLOPs 口径：Qwen3.8-27B 每 token 走的矩阵参数 = MLP 17.11B + 全注意力 16 层 1.68B（q 带输出门 12,288 维）+ GatedDeltaNet 48 层 5.54B = **24.3B**（词嵌入 1.27B 不算乘法；lm_head 只在监督段算；视觉塔另算、<1%）。LoRA + 梯度检查点：前向 2N + 重算 2N + 对激活求导 2N（冻结权重不求权重梯度）= 6N = 146 GFLOP；全注意力在 10K 长度约 +9 GFLOP。

## 三、评测（问题 ③）

### 3.1 时间去哪了

- run 内串行（一次一个请求），两个种子各 `--jobs 6` → 最多 12 个请求在飞；实测 Running 均值 6.65（另一半时间在工具里）。Little 定律：0.29 次调用 / s × 22 s / 次 ≈ 6.6 ✓。
- 每次调用在负载下的延迟 ≈ **8 s 首 token 前（排队 + prefill）+ 67 ms × 输出 token**。按输出长度分桶的中位延迟：≤40 token 8.2 s、40–100 8.9 s、100–300 10.5 s、300–700 34.7 s、700–1500 75.5 s、>1500 133 s。
- 合计：首 token 前 ≈ 1,960 × 8 s ≈ 15.7K s（38%）；decode ≈ 379K × 67 ms ≈ 25.4K s（62%）。**12.5% 的调用（输出 > 500 token，多是报告 / FINISH）占了 56% 的模型等待。**
- 可 GPU 并没有被吃满：prompt 吞吐均值只有峰值的 ~27%，KV ≤ 27%，等待队列 ≈ 0；但单请求 decode 从单跑的 ~90 tok/s 掉到 ~15 tok/s。"Deferred"（vLLM 0.32 `scheduler.py` 里 `ready_to_schedule` 为假时跳过的等待请求，最可能是 json_schema 语法在编译）均值 0.34 个 → 每次调用约 1.2 s。
- 能解释"又慢又不满"的候选（**未证实，靠 G4 拆**）：① 热降频同样作用于 serve（当时没采时钟）；② 每步都有其他请求的 8,192-token prefill 块，decode 请求被拖在长步里；③ json_schema 的语法 bitmask 在 engine 进程里逐请求计算（每次请求的 schema 都按状态重新生成，`bounded_schema`）；④ `--enable-lora` 的 punica 开销；⑤ API 进程每次解 8 张 1.5MP PNG 的 base64（单请求体 ~10 MB+）。

### 3.2 并发 12 → 24 / 48 的上限

- **GPU 下限**：要算的 prefill = 28.26M × (1 − 0.26) ≈ 20.9M token；按实测峰值 ~10K tok/s ≥ 35 min；decode 379K token 在批 20+ 时约 10 min，能部分叠在 prefill 里 → **整轮 48 run ≥ 45–60 min**。
- **关键路径下限**：最慢的 run 自己的工具时间（OCR 多次超时的 run 有 1,271–1,393 s 工具时间）+ 它的 ~45 次调用 → 25–30 min。
- 所以并发拉满的理论上限是 3 h → ~1 h（×3）。实际：
  - **并发 24**：预计 ×1.5–1.8（≈ 1.7–2 h）。**必须同时把 `--max-num-seqs` 从 16 提到 ≥ 32**，否则 16 就是硬上限；KV 24 × 16K ≈ 384K < 730K，不用动显存比例。
  - **并发 48**：KV 48 × 15K ≈ 720K ≈ 当前 730K 上限 → 要 `--gpu-memory-utilization 0.9`、`--max-num-seqs 64`；工具侧 48 进程 × 4 线程 = 192 > 128 vCPU，OCR（每进程 2 线程、本来就 22 / 31 次在 300 s 超时）会更慢 → **超时数变化会改变评测结果**，本轮不建议。
- **可比性约束（重要）**：评测不是计时无关的——OCR 300 s 超时、inspect 超时、看门狗 3600 s 都随负载变。提并发时要守住：负载平均 < ~100、每 run 的工具超时数不高于 r0base（OCR 超时 22 / 31）；看门狗建议放到 5400 s（单次调用变慢会把长 run 推过 3600 s）。

### 3.4 工具侧

- **跨 run 缓存：不做。** r0base 两个种子之间同一 (案例, URL) 的重复：open 4 / 607、acquire 4 / 110、search 1 / 236；训后评测本来就按 as_of 回放基线快照。
- **OCR 是工具侧最大的一块（12.3%），但这轮不能动**：`ocr range [0,120] s` × 2 fps ≈ 240 帧，rapidocr CPU（intra 2 线程）→ 31 次里 22 次撞 300 s 执行超时。提速会把"超时失败"变成"有结果"，与 r0base 不可比，而且改 OCR 参数 = 工具层 hash 变 → loop1（表 B）。
- compare_media 78 次里 56 次 failed（33 run-分钟）：原因没查（details 没有 error 字段），列 loop1。

### 3.5 状态渲染（loop1）能省多少输入

- 现在每次调用：[系统提示 3.4–4.5K][提示句 + 状态 JSON ~4.5K，每轮都变][图片 5.5–6.8K]。前缀命中 26% ≈ 系统提示。
- **稳定前缀布局**：[系统][任务 / 材料等不变字段][按首次出现顺序追加的图片][只追加的 evidence_view][history / latest_observation 放最后]。82% 的图片 token 上一轮刚发过 → 命中率 26% → **约 60–70%**，要算的 prefill **−45–55%**，视觉塔也少重算。
- **再压图片**：`maximum_model_image_pixels` 1.5MP → 每图 ~1–1.5K token、最多 8 张；非焦点图降到 ~0.5MP 或只在首次 / 被点名时附原图 → 输入再 −20–30%。
- 两项都改了模型输入，训练数据要按同一渲染重导出（训推同形），所以只能 loop1。

| 通信 | 每次更新 all-reduce LoRA 梯度 159M × 2 B ≈ 318 MB，PCIe 上 <0.5 s，相对 ~80 s 一步可忽略 | 每行要 all-gather 全量权重 3 遍（前向、重算、反向）≈ 165 GB / 卡：NVLink（~400 GB/s 实效）~0.4 s / 行（4%），**纯 PCIe ~7 s / 行（+70%）** |
| 负载不均 | 行长 1.6K–32K，每窗口 8 行分 4 卡各 2 行，随机分配估 15–25% 等待；**按 token 数在窗口内 LPT 分配**可压到 <5%，同一窗口 8 行的梯度和不变，不改配方 | 同 |
| 等价性要点 | DDP 默认对梯度**取平均**（÷ world_size）；现在的损失是 Σ_rows loss/grad_accum，要么 all-reduce 用 SUM、要么每卡乘 world_size；epoch 末余数窗口（HI 3369 = 421×8 + 1）有空卡也要参加 all-reduce；dropout RNG 每卡不同 → 与单卡不逐位相同（统计等价），单卡 checkpoint 可以接着用 DDP 续 | + PEFT 冻结参数、`use_orig_params`、检查点顺序、fla 自定义算子，工程风险高 |
| 结论 | **141 GB 卡选 DDP**（另一个对话在做） | 只在 80 GB **SXM（NVLink）** 卡上考虑；PCIe 80 GB 卡不要租 |

- 评测在多卡上：每卡一份 vLLM（数据并行），48 个 run 平分；不建议 TP（27B 单卡放得下，TP 只加通信）。
- 2 卡"1 训 1 服务"只在有两个种子或有 loop1 采样时才有意义：种子 1 评测与种子 2 训练重叠。

1. 训练与采样分卡：例如 3 卡 DDP 训练 + 1 卡 vLLM 采样；adapter 用 `/v1/load_lora_adapter` 热加载（`VLLM_ALLOW_RUNTIME_LORA_UPDATING=True` 已开），不重启 serve。

## 六、GPU 空窗 / 新机执行清单

**G0 烧机准入（负责人 10-20 定：迁 4×H200 时只收通过 G0 的机器；现这台 H200 NVL 随迁移换掉，不找房东）**

不过就退租换下一台（Vast 按小时计费，烧机 ~12 分钟），**在跑任何环境搭建之前做**。本机用一张正常卡 + 一张照旧机器实测数构造的假数据核过判定（前者 PASS，后者 FAIL：SM 906 MHz、91 °C、90% 热降频）。

`--think 9` = 实测每次调用之间的平均工具 + 其他时间（260 run-分钟 / 1,681 次）。`--format none` 让每次调用的输出长度与基线逐次相同（`min_tokens = max_tokens` = 录下的长度）。
