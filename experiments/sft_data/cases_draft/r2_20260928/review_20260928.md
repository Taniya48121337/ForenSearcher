最重要的三个问题：

1. **标成 must_cite=False 的标注来源并不是“可选”。** 这类来源只要没写进 any_one_of 组，就会各自成为一个 all 组，每份报告没引就记一条 major，两条就判 negative。受影响的有 441、63、98，其他几案各一条。
2. **2799 的原始核查没排除干净。** 标注里的 `original_claim_url` 其实是 PolitiFact 对同一条声明的核查（评级 False），调查代理现在可以直接读到结论。
3. **interval_iou 在核验器里的实际行为和案卷的设想不一致。** 这条检查不跑最终答案，却会对每个工作区报告都跑，`requirement: REQ1` 没有生效。这要改核验器，不是改案卷。

## 二、贯穿性问题

### 1. must_cite=False 的来源单独成组时，报告没引会被记 major（影响 11 案）

脚本 docstring 的设想是：“标注给出的来源……可能取不到，一律 must_cite=False”，也就是可以不引。核验器的实际行为不是这样：

- `Case.evidence_groups()`（cases.py:266）会把规则里没提到的 key 各自当成一个 `all` 组。
- `exec_checks.py:196-211` 对每个没被满足的组都记 `hard(OMITTED_REQUIRED_FACT)`。`must_cite` 只决定是否再加一条 `COMPLETED_WITHOUT_FINISHING`。
- `sufficiency.py:74-87` 对没覆盖、也不在已满足 any_one_of 组里的案卷项，同样记 `omitted_required_fact`。
- `errors.py:105` 把 OMITTED_REQUIRED_FACT 的默认严重度定为 MAJOR。按处置规则，报告有 2 个 major 就判 negative。

用试点证据模拟（`review/tmp/sim.py`）。下面这些组全部是 must=False、单独成组、试点从未取到：

| 案卷 | 这类单独成组的数量 | 后果 |
|---|---|---|
| averimatec:98 | 3（perma.cc ×3） | 不收窄的报告必然 negative |
| averimatec:441 | 2（两条推文） | 同时对准 REQ1、REQ2 的报告必然 negative，即使引了 Alt News |
| averimatec:63 | 2（sciencedirect、MNT） | 对准 REQ2 的报告必然 negative |
| 1766、2694、2799、652、699、1707、254、2872 | 各 1 | 每份在范围内的报告多一条 major |

修改原则：同一事实有试点取到的来源时，把标注来源并进同一个 any_one_of 组（441、2694、2799、98、1766、652）；同一 REQ 有多个取不到的标注来源时，把它们合成一组（63）；只剩一个标注来源、又没有替代项的（1707 budget_2018、254、2872、699 thewire）保留原样，残余风险见第四节。

旧案卷也有同样的写法，例如 true_17838107 的 `all:frames,fmcsa`、videosham 的 media_profile。旧审核记录把这类项叫“选”，其实并不可选。只不过旧案的这些项当时的 run 都取到了，问题没有暴露。

### 2. label_expected 的“不实”漏掉了“不属实”（12 个 Refuted 案）

`units.py:206-212` 的判法是：`label` 或任一 `alias` 小写后，是答案小写后的子串，就算命中。“不属实”这三个字里没有连续的“不实”，所以答案写“该说法不属实”会被记 omitted_required_fact。补上 `不属实` 只会让更多否定的写法命中，不会让“属实”类答案误命中。

另外两案补了本案特有的写法：2872 是伪造引语，补“捏造”“虚构”；392 的原文出自自称虚构的讽刺站，补“虚构”。

我没有补“误导”“没有证据”，因为它们会在 NEI 类措辞中出现。

残余风险：英文别名 `False` 按小写子串匹配，会命中 falsely、false-claim 这类 URL slug（例如 699 的 newsmobile、98 的 haqcheck）。只要答案用 E 编号引用而不贴 URL，影响就很小。

254 的处理不同：我建议删掉它的 label_expected，理由见逐案部分。

### 3. interval_iou（QVHighlights）：案卷与标注一致，但核验器没按设想执行

**与标注的一致性。** 四案的 `relevant_windows` 各只有一个窗口，而且和 `relevant_clip_ids × 2 秒` 对得上：0 是 19–25 对应 [38,52]，1 是 36–50 对应 [72,102]，2 是 0–74 对应 [0,150]，9167 是 42–59 对应 [84,120]。min_iou=0.5 的区分度也合理：
- qv0 r1 的“45–51 秒”IoU 为 0.43，不通过；r2 的“38–51.5 秒”通过。
- qv9167 r1 的“115–118 秒”不通过；r2 的“84–118 秒”IoU 为 0.94，通过。
- qv1 的“72–100 秒”、qv2 的“0–150 秒”都通过。

**核验器的问题，需要改代码，不在 JSON 里：**
- (a) `exec_checks.py:229` 只对 `_SCOPED_KINDS`（entity、numeric、date、status）判断作用域，interval_iou 不在其中。结果是案卷写的 `requirement: "REQ1"` 被忽略，每个工作区报告都要跑这条检查。只核对边界两侧、报告里只有“36–38 秒”这类短区间的工作区，会被记 hard unsupported_assertion；报告里完全没写区间的工作区，会被记 hard omitted。
- (b) `units.py:203-219` 的答案单元只核 entity、numeric、label、date，**最终答案的区间从来没有被核过**。
- (c) `_INTERVAL` 正则（exec_checks.py:14）要求第二个数后面紧跟“秒”或“s”，所以“0:38–0:52”这类写法会被当成“没给出区间”。

建议把 interval_iou 加进 `_SCOPED_KINDS`，并在 `check_answer` 里也跑一遍。在改好之前，这四案的区间检查实际上是在惩罚做边界复核的工作区。

### 4. 排除原始核查文章：实现覆盖面比 docstring 写的窄

- 运行时的 `KeyExclusion`（run_cases.py:130-146）只去掉 `web.archive.org/web/<时间>/` 这一种存档前缀。archive.ph、archive.today、perma.cc 以及 AMP 版（如 `indiatoday.in/amp/...`、`boomlive.in/amp/...`）都挡不住。它还保留 query，带 `?utm_...` 的原文地址会绕过排除（`_normalize_url` 保留 query，而匹配是相等或前缀加 “/”）。docstring 说“含存档地址”，实际只覆盖 Wayback 一种。
- 核验端 `exec_checks.py:217-220` 只把排除键转小写，被引 URL 用的是 `normalize_source_key`，路径不转小写。所以 AFP 这类路径带大写的原文（63 的 `doc.afp.com.33JQ83X`、660、98）即使被引用，也记不成 source_restriction_miss。运行时会先挡住，所以只是兜底失效，但应该修（两边都转小写）。
- 旧试点的 `source_policy.ArticleExclusion` 会读 `source_article_aliases.json`，新的 KeyExclusion 不读。唯一一条别名（660 去掉 -1 的地址）已经由脚本写进 excluded_keys，所以现在没有遗漏。
